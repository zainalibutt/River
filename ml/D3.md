# D3: one matched next-card spread ablation

1. Choose 32 strength × 4 potential buckets: the same 128 buckets and identical MLP dimensions, so training is cheap and matched.
2. Expected strength alone hides the distinction between a stable made hand and a draw; next-card percentile variance exposes that distinction in BOTH range inputs and value targets.
3. The implementation reuses the existing next-card hand evaluator and cached rank row; measured preparation was 12.5–15.7 seconds for 256 real spots on this machine.
4. The 0.73% turn bucket floor is much smaller than 2.94% error: changing output quantisation alone cannot explain the gap; this tests whether better range inputs improve learnability too.
5. A holding residual head/features would change model capacity and the training path; this ablation keeps the network, optimiser and loss unchanged and tests one representation choice.

## Historical evidence and limits

The READ-ONLY supplied findings log says potential-aware buckets remain **Open**.
Its text contains no `32x4` measurement. The existing trainer's `--turn-buckets 32x4`
reads side files written by `bot-turn-buckets-run.ts`: expected river strength ×
spread of showdown percentiles across rivers. **No prior success is assumed.**
The supplied B2 notes report the flat flop learning curve and +0.23 points from
cleaner labels; those are historical numbers, not results of this change.

For the flop, v1 spreads **made-hand percentiles across the 49 turn cards**,
excluding cards in each holding (47 valid turns per live holding). This matches
the existing flop expected-strength calculation, not final-runout equity.
Within 32 midpoint strength slices, variance is rounded to 1e-12 and holdings
are split into four midpoint potential quantiles; exact/rounded ties stay together.
Blocked holdings use 255 in caches and -1 in layouts. No labels inform features.
This reduces strength resolution and may worsen the floor. A null result would
reject this cheap proxy, not all potential-aware representations.

`-Data` takes one or more flop-end data folders; `-Exam` is a flop exam whose manifest specifies all
turn cards (`turnCards=0`). Up to 75,000 distinct training rows are frozen. Python can also be
invoked directly:

```powershell
& $py ml/d3_ablation.py --out art/out/d3-night --exam <data>/flop-exam2-5rr120 --data <data>/flopend-flop2 <more data folders>
```

Source directories are READ ONLY. Everything generated lives in the chosen output
under this worktree. Identity duplicates `(runSeed, worker, spot)` are removed;
conflicting copies fail. Finished shard hashes and request parameters freeze the
snapshot on reuse, including after source folders receive more data. Feature caches
have source/output SHA256 hashes and atomic shard-level writes; restarts recompute
only missing or invalid caches. An interrupted training fit restarts from epoch one.
Use a new output directory to change sources or snapshot limits.

## Matching, parity, and outputs

Both fits use the same immutable 90/10 split, seed 203, 100 epochs, width 512,
depth 3, batch 512, learning rate 0.001, loss and cosine schedule. Both use the
same best-held-out-bucket-error selection rule; the exam never selects epochs.
The exported split SHA256, row counts and dimensions must agree. Deterministic
PyTorch operations are enabled for BOTH snapshot fits. Jobs run sequentially;
the existing trainer keeps tensors in RAM if GPU memory is tight.

For EACH trained model, `export_value_parity.py --d3-model` exports four real
records plus one empty-player-range stress case, Python trainer inputs, cached
bucket ids and actual PyTorch outputs.
`bot-d3-parity-run.ts` rebuilds the feature layout from boards and ranks, compares
all 1,326 ids exactly, compares inputs within 2e-6 relative/absolute and network
and per-holding outputs within 2e-5. These allow float32 reduction differences.
It fails before exam reporting if feature or export parity fails. Existing
PyTorch-fixture forward tests also remain in the targeted test set.

The existing `bot-flop-end-check.ts` grades both on exactly the same frozen exam;
its metrics and depth bands remain unchanged. `summary.csv` is one table of
model × band, spot count, every-holding error and held-hand error (% pot).
`summary.json` adds matching evidence and stage timings; per-stage logs sit beside it.

Estimates for one RTX 2060 Super, NOT a measured full run:
